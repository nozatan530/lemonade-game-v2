## 2026-09-25 GM 画面

**判断**：
- 自動の締切は GM の端末で行う。締切の3.5秒後（ルールが提出を受け付ける「締切＋3秒」より後）に締め切り、ぎりぎりの提出を取りこぼさない。参加しているチームが全員提出したら、早めに締め切る（設定でオフにできる）。
- ブラウザは裏にしたタブのタイマーを遅らせるので、タブに戻ったとき（`visibilitychange`・`focus`）にも締切を確かめる。
- 締切の処理と翌月の開始は、何度押しても結果が変わらない（sync の関数が段階を確かめる）。GM 画面を読み込み直しても、データベースから状態を復元する。
- 入力中は、GM にだけその月の市場予算を見せる（進行の説明に使えるように）。
- エミュレーター接続時だけ、「開発用：テスト GM でログイン」ボタンを出す（自動テストや動作確認で Google のポップアップを使わないため）。このアカウントはエミュレーターの中にしか存在しない。

## 2026-09-25 販売チーム画面

**判断**：
- シードを含む `config` は GM だけが読めるようにし、チームには必要な項目だけの `public` を見せる。シードがわかると、市場予算や原価の変動を計算で先読みできてしまうため。
- 入力欄の初期値は「今月の自分の提出 → 先月の自分の提出 → 先月の結果 → 既定値（レモン50・砂糖50・300円）」の順で決める。毎月の入力を短くするため（50分の制約）。既定値の 300円 は旧版と同じ。50個はバリスタ1人の上限。
- 入力中の見込み（作れる数・かかるお金・全部売れたときのもうけ）は engine の `previewDecision` で計算する。実際の処理と同じ関数を使い、全部売れたときの結果と一致することをテストしている。
- 価格0で提出しようとしたら「静観にしますか？」と確認し、はいなら静観として送る（TODO を解消）。
- ログイン状態は役割（GM／チーム／全体表示）ごとに分けて保存する。同じブラウザで GM とチームを開いても混ざらないようにするため。開発中だけ、`device` を変えると1つのブラウザで別の端末のふりができる。

## 2026-09-25 データの置き方とセキュリティルール（sync）

**判断**：
- 月のキーは `m01`〜`m12`。連番の数字キーは、データベースが配列に変えて返すため使わない。
- 読み取りの許可は `games/{code}` にまとめて付けず、子ごとに付ける。上の階層で許可すると下の階層すべてに効き、締切前に他チームの提出（価格など）が見えてしまうため。
- 提出（`subs`）は本人のチームと GM だけが読める。全体表示やほかのチームには、中身を含まない「提出済み」の印（`submitted`）だけを見せる。
- その月の**市場予算は GM だけが読める**（`hidden`）。結果が出たら公開する。旧版の「予報（幅で示す）」はこの最小版には入れない。
- 提出時刻はサーバーの時刻（`submittedAt === now`）でなければ受け付けない。同じ価格の端数の配分に使うため、ごまかせないようにする。出し直したら提出順も更新する（旧版と同じ）。
- 締切の処理は、結果・月末の状態・補った決定・進行の状態を1回のまとめた更新で書く。結果は一度しか書けないルールにして、2回締め切っても結果が変わらないようにする。
- 古いゲームの掃除は、新しいゲームを作るときに、作成から30日以上たった自分のゲームを消す（終了日ではなく作成日で判定する）。

**理由**：Spark プランではサーバー側の処理がないため、公平さとデータの守りはセキュリティルールで担保する。ルールはエミュレーターでテストする（`npm run test:emu`）。

## 2026-09-25 期のはじめからバリスタを1人雇っている

**判断**：設定に「最初のバリスタ人数」（`initialBaristaCount`、初期値1人）を加え、全チームがその人数を雇った状態で期を始める。

**理由**：0人から始めると、1か月目の締切に間に合わなかったチームは四半期の決定がないため、最初の四半期（3か月）ずっと販売できない。1人いれば、未提出でも「前月と同じ決定」で販売に参加できる。旧版には該当する仕組みはない（毎月入力していたため）。

## 2026-09-25 月の進め方を engine に置く

**判断**：締切の処理（`closeMonth`：未提出の補完 → 1か月の処理 → 実際の決定の記録）、期のはじめ（`startTerm`）、翌月の条件（`openNextMonth`）を `src/engine/month.ts` の純粋関数にした。

**理由**：GM 画面にゲームの仕組みを書かないため（CLAUDE.md 開発ルール1）。GM 画面と sync は、これらの結果をデータベースに書くだけにする。

## 2026-09-25 シナリオのお知らせ文から暦の月の表記を消す

**判断**：シナリオのお知らせ文にあった「1月。」「2月。」などの表記を消した。月の表示は、画面側で期の開始月（`startCalendarMonth`）から組み立てる。

**理由**：v2 は4月始まりが標準なので、1か月目に「1月。」と出るとずれる。旧版との比較テストでは、旧版の文から月の表記を除いて比べている。

## 2026-09-25 初級ルールは旧版の計算を移植する

**判断**：初級の計算は旧版（`legacy/index.html`）と同じ結果になるように移植する。テストで旧版の関数を実際に動かし、同じ入力で結果が一致することを確かめる（`src/engine/__tests__/legacy-parity.test.ts`）。

**理由**：旧版は授業で使われてきた実績がある。まず同じ動きを再現してから、中級以上の要素を足す。

旧版と同じにしたもの：
- 乱数（`seededRand`）。状態を持たず、(シード, 月×100＋番号) から値を決める。まれに1ちょうどを返す性質と、シードと番号を文字列でつなぐ性質もそのまま残した。
- 市場予算の変動（基準額 × (1 ± 変動幅)、1,000円単位）と原価の変動（fixed / random / trend / shock）。変動は常に初期値を基準にする。
- シナリオ3種（夏の繁忙期・原材料高騰・市場乱高下）。market の値は2チーム基準なので、チーム数に比例して拡大する。
- 月ごとの単価の優先順位：シナリオ ＞ 自動変動 ＞ 前月の単価。GM の手入力による上書きは engine の外で行う。
- 1か月目は、シナリオがあっても初期単価と自動の市場予算を使う（旧版の癖。直すかどうかは試行の後に決める）。
- 購買の配分：安い順に買う。同じ価格なら均等割にして、割り切れない分は提出順に、各チームの上限まで渡す（旧版のコメントには「ラウンドロビン」とあるが、実際のコードの動きに合わせた）。

## 2026-09-25 初級の原価は「仕入れた分」で計上する

**判断**：初級では、仕入れた材料の代金をその月の原価にする（在庫として繰り越す分も、買った月の費用になる）。中級以上では「販売に使った分」を原価にする方式を導入する予定。

**理由**：旧版と同じ結果にするため。ただし、在庫を持ち越すと、買った月の利益が小さく、使った月の利益が大きく見える。期末の振り返りでは、この点を説明できるようにする。

## 2026-09-25 バリスタの人数は四半期ごとに決める

**判断**：バリスタの人数は設計書どおり四半期の決定（1・4・7・10か月目）にする。静観した月も、雇っているバリスタの給与はかかる。

**理由**：毎月の入力を減らすため（50分の制約）。旧版は毎月入力し、静観の月は給与0円だったので、この点は旧版と異なる。旧版との比較テストでは、四半期に決めた人数を旧版に毎月入れて比べている。

## 2026-09-25 販売上限（maxSell）は任意の入力として残す

**判断**：「最大何杯売るか」を任意の入力項目として残す。省略したら、作れるだけ売る。

**理由**：材料を在庫として持ち越す作戦をとれるようにするため。
**50分の制約への影響**：毎月の入力が最大3項目になる。画面では既定値を「作れるだけ」にして、省略しても進められるようにし、1か月あたりの操作時間が増えないようにする。

## 2026-09-25 未提出チームは前月と同じ決定で処理する

**判断**：締切までに提出しなかったチームは、前月と同じ月の決定で処理する。前月がなければ（1か月目）静観にする。四半期の決定は補わず、いまのバリスタ人数のままにする。補った提出は、提出済みのチームより後の順番として扱う。

**理由**：設計書どおり。旧版は静観扱いだった。タイマーで自動締切にするとき、提出が間に合わなかったチームが急に販売ゼロになるのを避ける。
